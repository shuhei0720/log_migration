# ログの送信先を切り替える手順

現在のログ送信を続けたまま、新しい保存先への送信設定を追加します。設定値を確認してから、元の診断設定とVM・VMSSのDCR関連付けを削除し、移行後の設定全体を最終確認します。保存済みのログは元の保存先に残ります。

このフォルダが移行スクリプトの正本です。コマンドはリポジトリのルートから実行してください。コードの説明は[学習ガイド](CODE_LEARNING.md)、本番作業後の判定は[確認表](POST_MIGRATION_CHECKS.md)にあります。

## 作業の流れ

|ファイル|行うこと|次へ進む条件|
|---|---|---|
|`precheck.ps1`（任意）|作成先の名前や、診断設定の空き枠を事前に調べる|`precheck_results.csv`のResult列がすべてOK|
|`step1_copy.ps1`|元の設定を記録し、新しい保存先と送信設定を作る|エラーなく終了する|
|`step2_verify.ps1`|Azureの設定値と、作業記録の値を比べる|`verify_results.csv`のResult列がすべてOK|
|`step3_delete.ps1`|旧診断設定と旧DCR関連付けを削除する|削除前にもstep2を実行し、すべてOKなら削除を始める|
|`step4_final_check.ps1`|旧設定の削除と、保存先・新送信設定・適用除外の状態をまとめて確認する|`final_check_results.csv`のResult列がすべてOK|
|`rollback.ps1`（必要時）|旧設定を戻してから、今回追加・変更した送信設定を元に戻す|エラーなく終了し、旧設定が記録の値に戻る|

データ収集ルール（DCR）は、VMから収集するログと送り先を決めます。DCR関連付けは、そのルールをVM・VMSSに結び付けます。**step3は関連付けを削除し、旧DCR本体は残します。**

## 1. 実行環境と入力を用意する

PowerShell 7とAzure CLIを使います。対象サブスクリプションのOwnerとして`az login`を済ませてください。対象サブスクリプションを、管理グループで割り当てたポリシーから適用除外にできる権限も必要です。Windows PowerShell 5.1では実行できません。

### common.ps1に移行元と環境を指定する

先頭の6変数を確認します。旧DCR・管理グループ・ポリシー割り当てには、既存のIDを指定します。

|変数|指定する内容|
|---|---|
|`$targetWorkspaceId`|現在のLog AnalyticsのリソースID。このワークスペース宛ての診断設定を移行する|
|`$environment`|今回作業する環境。`prod`・`stg`・`dev`のいずれか|
|`$newDiagnosticSettingName`|追加する診断設定の名前。全リソースで同じ名前を使う。既定値は`setByAzurePlatformTeam`|
|`$location`|新しいリソースグループ・Log Analytics・DCRを作る地域。既定値は東日本（`japaneast`）|
|`$environmentSettings`|各環境の旧DCR2本、管理グループ、ポリシー割り当て3件。指定された値を設定済み|
|`$policyReferenceIds`|3件目のポリシー割り当てから除外する12個の参照ID。指定された値を設定済み|

ストレージアカウントは診断設定を付けるリソースと同じ地域に用意します。地域が空欄・`global`なら東日本です。`LogDestination=Storage`では、移行先のLog Analytics自身も送信するため、その地域（`$location`）にも用意します。

### CSVに作業先を指定する

[CSV作成スクリプト](../tools/README.md)で環境別に作成できます。手入力する場合は、次の例をコピーして記入します。

例のリソース名は開発の`dev`で統一しています。検証・本番では、名前の環境部分も`stg`・`prod`へ変更してください。

```powershell
Copy-Item .\migration\targets.example.csv .\migration\targets.csv
```

`targets.csv`には、1サブスクリプションにつき1行を書きます。

|CSV列|指定する内容|
|---|---|
|`SubscriptionName`|サブスクリプションID、または一意に決まる名前|
|`ResourceGroup`|保存先を入れるリソースグループ名。必須|
|`StorageAccount`|`jpe`を1か所含む、小文字英数字3～24文字の名前。診断ログの送り先が`Storage`なら必須|
|`WorkspaceName`|移行先のLog Analyticsワークスペースの名前。必須|
|`LogDestination`|診断ログの送り先。`Storage`・`Log`・`None`・空欄から選ぶ|
|`VmLogDestination`|`Log`ならVMログ用の新DCRと関連付けを作る。`None`・空欄なら作らない。送信先はLog Analytics固定|

6列すべてが必要です。列の欠落はエラーにし、値を空欄にする指定と区別します。

`None`・空欄の側は新しい送信設定を作らず、step3で旧設定を外して送信を終了します。**保存先は用意します。** Log Analyticsはすべての行、ストレージアカウントは名前がある行が対象です。ストレージの配置先地域が0件なら、東日本に1つ用意します。

### 作成先と既存の保存先を確認する

指定のリソースIDにリソースグループ・Log Analytics・ストレージが存在し、予定の地域と一致すれば再利用します。地域が違えば、保存先や送信設定を変更する前に停止します。

再利用する保存先の保持期間・冗長性・通信・暗号化などは変更しません。既存ストレージのBlob設定・ライフサイクル・Defender、既存Log Analyticsの作成済みEvent・Syslogテーブルもそのままです。テーブルが未作成の場合だけ、合計1,095日保持で作成します。

ストレージ名の`jpe`だけをAzure Naming Toolの地域略称へ置き換えます。取得先の`raw.githubusercontent.com`へ接続できる必要があります。初めて作るストレージは、同じ地域のZRSを優先し、非対応ならLRSを選びます。ZRS・LRSのどちらも使えない場合や、名前が別RG・別サブスクリプションで使用済みなら、作成前に停止します。

ストレージ本体やその子サービスの診断ログを、そのストレージ自身へ送る構成はAzureで作成できません。該当する場合は保存先や送信設定の作成前に停止します。CSVを`Log`へ変更するか、別の保存先を指定してください。

## 2. 結果を確認しながら実行する

各コマンドを一つずつ実行します。エラーやNGがあれば、次へ進みません。

```powershell
az login

# 任意。前日などに確認する。
pwsh.exe -NoProfile -File .\migration\precheck.ps1

# 旧設定を残して新設定を準備する。
pwsh.exe -NoProfile -File .\migration\step1_copy.ps1

# verify_results.csvを確認する。
pwsh.exe -NoProfile -File .\migration\step2_verify.ps1

# 確認後、旧設定を削除する。
pwsh.exe -NoProfile -File .\migration\step3_delete.ps1

# 移行後の設定全体を確認する。
pwsh.exe -NoProfile -File .\migration\step4_final_check.ps1
```

### precheck：作成前の問題を見つける

各サブスクリプションで、旧診断設定と旧DCR関連付けを探します。ストレージの子サービスとRedisの子DBも調べます。指定ポリシー3件の適用と12参照ID、保存先の地域、新規ストレージ名の空きと利用できる冗長性、新診断設定名の重複と上限5件を確認します。

名前確認に必要な`Microsoft.Storage`が未登録なら登録し、完了を待ちます。保存先や送信設定は作成しません。この利用登録は、後の確認がNGになった場合も、切り戻した場合も解除しません。

結果は`precheck_results.csv`に出し、作業記録は保存しません。前日にも実行できますが、step1はこの結果を使わず、作業直前に調べ直します。precheckは作業記録を読まないため、作成済みの新診断設定があれば同名の重複としてNGにします。作業の再開にはstep1を使います。

### step1：元の設定を残し、新しい送信設定を作る

CSVの順に、サブスクリプションごとに次を行います。

1. 作業記録を読み、今回の入力と比べる。現在の旧設定・作成先・ポリシーも調べ、新規ストレージのZRS・LRSを地域に応じて選ぶ。名前確認が必要なら、ここで`Microsoft.Storage`の利用登録を済ませる。
2. 適用除外・保存先・保持期間・DCR・診断設定について、Azureへ渡す値と変更前の値を用意する。この段階ではAzureへ書き込まない。
3. 旧設定・作成する値・変更前の値をJSONへ保存する。再実行では前回の記録と比べ、新たに見つかった設定を追加する。保存後に適用除外や保存先などを変更する。
4. ポリシーの適用除外、保存先と保持期間、DCRと関連付けの順に設定する。再利用する保存先は変更しない。同じ値なら書き込みを省き、残りの未登録サービスは利用登録する。書き込むたびにAzureから読み直し、記録の値と比べる。
5. 診断側がStorage・Logなら、新診断設定を最大5件同時に作る。旧リソースではログ・メトリックを引き継ぎ、移行先のLog AnalyticsとDCR自身はallLogsだけを有効にする。作成後もAzureから読み直して比べる。

コードの番号付きブロックコメントも、この1～5に対応しています。

ポリシーの適用除外（Waiver）は期限なしです。最初の2割り当ては全体、3件目は指定した12参照IDを除外します。3件すべての作成・照合が済んでから保存先を作ります。失敗したサブスクリプションでは、保存先の作成へ進みません。

新DCRと関連付けは、旧DCRの関連付けがあり、VM側がLogの場合だけ作ります。新DCRは固定のWindowsイベント（Application・Security・System）とSyslogを収集し、名前はワークスペース名の先頭`log`を`dcr`へ置き換えます。新診断設定は、旧設定のログの格納方式も引き継ぎます。

移行先のLog Analytics自身の診断設定も、共通の`$newDiagnosticSettingName`で作ります。`LogDestination=Storage`なら同じ地域のストレージへ、`Log`なら自身へ送ります。`allLogs`だけを有効にし、メトリックは有効にしません。`None`・空欄なら作りません。この設定もstep2で確認し、step3では残し、切り戻しでは削除します。今回の移行先DCRを用意する場合は、そのDCR自身にも同じ名前・送信フラグで診断設定を付けます。`Log`なら新しいLog Analyticsへ、`Storage`ならDCRと同じ地域のストレージへ送ります。DCRは`allLogs`のみを指定し、未対応の`audit`は指定しません。

新規作成する保存先には、次の値を設定します。再利用する保存先には適用しません。

|保存先|設定する値|
|---|---|
|リソースグループ・Log Analytics|地域は`$location`。ワークスペースの保持期間は90日。取込・クエリのパブリックアクセスを有効化し、リソースまたはワークスペースの権限でログを参照できるようにする|
|地域別ストレージアカウント|StorageV2。Standard_ZRSを優先し、非対応地域ではStandard_LRS。インフラ暗号化と、バージョン単位の不変性のサポートを有効化。共有キー・Blobの匿名公開は無効。HTTPSとTLS 1.2を使用。公開ネットワークはDisabled、ネットワーク規則は既定拒否・AzureServices例外|
|Blobとストレージの追加設定|Blobバージョン管理を有効化。最終更新から1,095日を超えたappendBlobを削除するルールを追加。個別のDefenderを無効化|
|Event・Syslogテーブル|合計保持期間を1,095日にする。旧DCRの関連付けがなくても、`VmLogDestination`がNone・空欄でも設定する|

このスクリプトが作成した保存先は、冗長性を含めて記録の値で確認・補修し、再実行で冗長性を選び直しません。再作成する際、記録した冗長性がその地域で使えなければ停止します。補修時は、追加されたIP・VNet規則、Log Analyticsのほかのfeatures、別名のライフサイクルルールを残します。DCRのマネージドIDも残し、旧送信設定は削除しません。

診断設定の調査も、各サブスクリプション内で最大5件を同時に行います。調査や保存先の作成に失敗した場合は、そのサブスクリプションの残りを止めて次へ進みます。新診断設定の並列作成では全件の結果を集め、成功した設定を残します。全サブスクリプションの処理後、未完了の設定を`copy_failures.csv`に出します。

接続切断・通信タイムアウト・一時HTTPエラーは、初回を含め最大4回試します。1回の接続・応答待ちは5分です。対応するPowerShellでは、本文受信中の無応答も5分で再試行します。作成やテーブル反映を待つ時間には全体の上限を設けず、Failed・Canceledなら停止します。

### step2：新しい設定の値を比べる

作業記録の`Body`とAzureの保存先・新設定を1件ずつ比べます。再利用する保存先は有無と地域だけを確認します。新設リソースグループは存在、今回設定したEvent・Syslogは合計保持期間の明示設定も確認します。記録がないサブスクリプションはNGです。

旧設定も探し直し、記録にない追加や値の変更をNGにします。削除の再開にも使うため、すでに削除された旧設定は許可します。

Azureは変更せず、結果を`verify_results.csv`へ出します。Result列がすべてOKならstep3へ進めます。NGはReason列とExpected列で原因を調べます。

### step3：旧送信設定を削除する

最初にstep2で全サブスクリプションを確認し、1件でもNGなら削除を始めません。

全サブスクリプションの旧DCR関連付け、その後に旧診断設定を削除します。各削除の直前にも、旧設定と新設定が作業記録どおりか確認します。`None`・空欄の側は新設定を確認せず、旧設定を外して送信を終了します。

値の不一致やAPIエラーは`delete_failures.csv`に記録し、失敗したサブスクリプションの残りを止めます。ほかのサブスクリプションは順次処理を続け、全対象の処理後に失敗を通知します。保存先・ログ・新設定・適用除外は残します。再実行では削除済みを省略します。

### step4：移行後の設定全体を最終確認する

step3の後に、同じcommon設定・CSV・作業記録で実行します。記録した旧診断設定・旧DCR関連付けが存在せず、保存先・新診断設定・DCR・関連付け・適用除外が記録どおりであることを確認します。旧送信先を使う設定も探し直し、記録にない追加をNGにします。

新設RGは存在だけを確認し、ほかの新設保存先は保持期間やセキュリティ設定も比べます。再利用した保存先は存在と地域だけを確認します。`None`・空欄の側も旧設定の削除を確認します。新設定として値を比べるのは、作業記録にあるIDだけです。

取得失敗や不一致があっても、残りの項目とサブスクリプションを確認します。結果は`final_check_results.csv`へ出し、NGがあればエラーで終了します。Azureと作業記録は変更しません。原因を直した後は再実行できます。

## 3. 途中で止まった作業を再開する

**common設定・CSV・recordsを変えずに**、止まった工程を再実行します。step1は設定済みを省略し、新たに見つかった旧設定を記録へ追加します。最初に記録した変更前の値は残し、記録済みの旧設定が消失・変更していれば停止します。

作業記録は`records/<環境>/<サブスクリプションID>.json`です。設定値だけを保存し、サブスクリプション全体やログデータは保存しません。

|記録の項目|入っている情報|
|---|---|
|`Context`・`Target`|移行元ワークスペース・環境・旧DCR・新診断名と、その行のCSV値|
|`OldSettings`|旧診断設定と旧DCR関連付けのID・種類・復元する設定値|
|`Destinations`|保存先・保持期間の設定IDと設定値。再利用する保存先は`Reuse=true`と地域だけを記録|
|`NewSettings`|新診断設定・DCR・関連付け・適用除外の作成値`Body`と変更前の値`Before`|

`Before=null`は、その設定が作業前には存在しなかったことを表します。

|結果ファイル|確認する内容|
|---|---|
|`precheck_results.csv`|サブスクリプションごとのOK／NGと理由|
|`copy_failures.csv`|作成できなかった設定のID・理由・作成予定の値|
|`verify_results.csv`|設定IDごとのOK／NG。NGなら理由と予定値も記録|
|`delete_failures.csv`|削除を止めた設定のID・理由・元の値|
|`final_check_results.csv`|移行後の最終確認。設定IDごとのOK／NG・理由・予定値|
|`rollback_failures.csv`|切り戻しを止めた設定のIDと理由|

入力エラーは結果CSVより先に画面へ出る場合があります。step3冒頭の失敗は`verify_results.csv`を見ます。旧設定の削除がすべて成功すると、前回の`delete_failures.csv`は削除します。削除前の全件確認でNGになった場合は、前回分を残します。

## 4. 旧設定へ切り戻す

step1・step3の途中でも完了後でも、同じ`rollback.ps1`を使います。common設定は記録作成時と同じ値にし、CSVは使いません。

```powershell
# 全体を戻す。
pwsh.exe -NoProfile -File .\migration\rollback.ps1

# 指定Subだけを戻す。PowerShell 7から実行する。
.\migration\rollback.ps1 -SubscriptionIds '対象Sub ID'

# 複数Subを戻す。
.\migration\rollback.ps1 -SubscriptionIds '対象Sub ID 1', '対象Sub ID 2'
```

切り戻す設定の現在値を作業記録と比べ、記録にない変更があれば書き込み前に停止します。旧DCR関連付け、旧診断設定の順に全対象へ復元してから、新しい設定を戻します。途中で失敗したサブスクリプションの残りは止め、ほかのサブスクリプションは続けます。旧設定を復元できなかったサブスクリプションの新設定は残します。

|設定|切り戻し後の状態|
|---|---|
|旧診断設定・旧DCR関連付け|作業記録の内容で復元する。すでに同じ値なら変更しない|
|今回追加した新診断設定・新DCR関連付け|削除する|
|移行時に変更した既存DCR・関連付け|変更前の値`Before`へ戻す|
|今回作成したDCR本体|残す|
|ポリシー適用除外|今回作成したものは削除する。元からあったものは残す|
|保存先・保存済みログ|残す|

旧診断設定を戻す空き枠がなければ、ほかの設定を消さずに停止します。復元後もAzureの値を比べます。失敗は全対象の処理後に`rollback_failures.csv`へまとめて通知します。原因を解消して同じ記録で再実行すると、復元済みを省略して未完了の設定を戻します。ポリシー修復タスクは使いません。

`targets.csv`・`records/`・結果CSVはGit管理外です。作業が終わるまで、同じフォルダに保管してください。

## common.ps1の役割

利用者設定と5つの共通関数を読み込みます。通常はCSV検査・サブスクリプション名のID解決・地域略称の取得も行い、`-SkipCsv`付きなら省きます。関数の処理と引数は各ヘルプ、呼び出し後の流れは[学習ガイド](CODE_LEARNING.md)を参照してください。
